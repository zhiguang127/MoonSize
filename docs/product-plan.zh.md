# MoonSize v0.3 交付计划与最终形态

评审基线：2026-09-23，提交 `3f0c9a0`。本计划依据当前代码与仓库验证记录；本次是实现审阅，没有重新运行测试或核验远端 Actions。目标是交付一个外部 MoonBit 开发者能够独立安装、解释 Wasm 体积变化并接入 PR 检查的 v0.3。

**目前已具备的能力**

| 层次 | 当前实现 | 验收边界 |
| --- | --- | --- |
| 核心统计 | 区段、函数体、符号解码、资源限制和字节核算 | 支持范围内的结构解析；不是完整 Wasm 验证器 |
| L2 归因 | 包汇总、唯一原始符号匹配、双侧覆盖率、未知项保留 | 名称匹配不证明行为相同；单侧名称不证明源码新增或删除 |
| L3 引用 | 直接调用、函数引用、入口与声明根、已知包含路径 | 动态目标和解码失败明确保留未知；不能据此计算可删除体积 |
| 工程决策 | raw/gzip/Brotli 预算、SHA-256 构建记录、条件检查、摘要和 JSON 文件输出 | CLI 能比较调用方提供的两份产物；基准选择与获取尚由调用方负责 |
| 展示 | 本地 Worker、取消与超时、中英报告、函数搜索分页、引用跳转、离线 HTML | 浏览器仅测 raw；CLI 报告可携带压缩指标和构建条件 |
| 验证 | 两个固定上游源码案例；历史四后端各 55 个测试；上一轮 Node 37 个测试通过 | 最新一轮复用了核心构建产物；仓库记录尚未提供 v0.3 远端成功证据 |

**影响交付的具体缺口**

1. `package.json` 仍为 `private: true`，没有命令入口或发布文件清单。CLI 顶层直接导入 `_build/js/release/build/moonsize.js`；缺少构建产物时，连帮助信息也无法正常启动。当前使用方式要求克隆仓库并构建。
2. `.github/workflows/ci.yml` 比较固定的 before/after demo，没有验证目标分支提交与 PR 提交之间的基准获取、保存和比较。Node 配置仅固定主版本 `24`，尚未与压缩复现所需的精确运行时记录形成完整验收流程。
3. `scripts/analyze-cases.mjs` 直接调用核心并生成报告，外部案例尚未在构建时生成 v0.3 记录，也没有贯通 CLI 的综合策略与摘要。
4. `--json-file` 已保护输出路径，但参数、读取、记录绑定等前置错误不生成新 JSON。如果复用路径，上次成功结果可能仍在，失败任务上传证据时容易混淆。需定义输出文件的生命周期和失败产物语义。
5. 独立开发者接入记录、三分钟演示和发布材料仍未完成。README 引用的 `docs/proposal.zh.md` 在当前受版本管理的文件中不存在，交付前需要补齐或修正链接。

**下一步按四个里程碑推进**

| 顺序 | 工作与交付物 | 完成标准 |
| --- | --- | --- |
| M1：可分发的 CLI 候选包 | 构建发布目录，包含 CLI、编译好的 MoonBit JS 核心、报告模块和许可证；配置命令入口、版本输出及打包检查；明确 JSON 输出失败语义 | 在仓库外的临时目录安装候选包，仅有受支持 Node、没有 MoonBit 和仓库 `_build` 也能执行帮助、analyze、diff、record；退出 0/1/2 都有对应验证；前置失败不会被误认成旧的成功报告 |
| M2：真实产物的 v0.3 验收 | 外部案例构建时生成绑定记录、实际依赖指纹和源码/补丁身份；通过 CLI 输出压缩指标、策略、JSON、HTML 和摘要；固定验证运行时 | CommonMark 优化前后条件匹配，字节核算与行为对照通过；预算通过和故意超限各留一套证据；保留原有 TOML 案例检查；v0.3 当前提交在远端完整跑通 |
| M3：真实 PR 接入模板 | 提供一个单产物 CI 示例，分别在隔离目录构建明确的目标分支 SHA 与 PR head SHA；保存产物及绑定记录，比较后上传报告 | 正常 PR、超预算、构建条件不同、缺少基准、损坏产物都有明确结果；基准缺失不能显示为预算通过；失败仍保留本次有效诊断；产物来源可追溯且 PR 不覆盖既有基准 |
| M4：外部试用与发布 | 一位未参与实现的开发者按文档完成接入；修复阻塞问题；完成快速开始、兼容性与 schema 说明、演示脚本、发布说明和校验清单 | 试用者无需作者代操作即可生成并解释报告；在干净环境完成安装、分析、CI 失败诊断和离线报告查看；候选包通过上述门槛后再发布 |

M1、M2 应先完成。M3 首先用同一固定环境构建两份明确源码版本，降低接入复杂度；跨工作流下载历史 artifact、缓存与多产物汇总在真实需求出现后扩展。依赖升级导致条件不同时，需要明确展示差异并由策略决定是否阻止，不能修改声明来制造一致。

M2 只记录本次实际构建信息。旧案例文件不能补造为已验证的构建记录；优化后源码身份应同时保留上游提交和补丁摘要。

M1 的输出设计应在路径保护成功后写出本次结果或错误，采用临时文件完成后替换，避免半写入 JSON；路径校验失败时不得触碰冲突的输入或配置。对无法写出诊断的情况保留明确退出码，并让 CI 使用每次运行独立的结果目录。验收应覆盖旧结果已存在、输入读取失败、哈希绑定失败和输出写入失败。

**最终用户拿到什么**

| 交付物 | 用户操作 | 预期结果 |
| --- | --- | --- |
| 可安装的 CLI | 通过版本化候选包或正式包安装，运行 `moonsize analyze/diff/record` | CLI 使用者不需要 MoonBit 编译器；保留机器可读 JSON、预算退出码和人类可读摘要 |
| 交互报告与浏览器入口 | 浏览器选择本地 Wasm，或直接打开 CI 下载的 HTML | 看到总量、增长、策略状态、构建条件、主要区段/包/函数变化；可以追踪引用和查看未知项；离线 HTML 无需服务端 |
| CI 接入模板与策略示例 | 指定构建命令、产物路径和预算，并明确基准来源 | PR 上有可审阅的摘要与可下载报告；预算失败与工具错误可区分；默认不自动发评论 |
| MoonBit 核心库 | 调用 `analyze`、`compare`、`check_budget`、`inclusion_path` | 核心接口、版本和分析 schema 有文档；作为单独的库发布交付物验收 |
| 复现和展示材料 | 运行案例脚本或按三分钟演示步骤操作 | 能复现一次真实优化，追溯工具链、输入哈希、行为验证和体积变化 |

安装包优先交付 CLI。Mooncakes 核心库与静态浏览器入口分别完成自身安装/部署验收；不把多个分发渠道的配置混为同一项完成度。

报告阅读顺序应固定为：本次是否通过及失败原因 → raw/压缩体积与变化 → 构建条件与数据完整性 → 主要增长来源 → 函数与引用证据。保留搜索、分页、中英切换和离线能力。对 strip 导致的名称缺失、部分引用图和未测量压缩提供紧邻数据的解释；不自动推导源码行、运行时执行或删除收益。

示例最终使用流程如下（目标命令形态，当前尚未提供可安装的 `moonsize` 命令）：

```sh
moonsize diff baseline/app.wasm current/app.wasm \
  --before-build baseline/app.build.json \
  --after-build current/app.build.json \
  --policy moonsize-policy.json \
  --json-file results/result.json \
  --html results/report.html \
  --summary results/summary.md
```

**v0.3 的完成定义**

当干净环境安装、真实构建比较、PR 策略失败、离线报告审阅、外部独立接入都完成验收，并有当前版本的远端证据和发布包时，才称为可交付。现有功能主体已经实现；交付成熟度应逐项记录，不能仅用一个百分比代表。

函数推断匹配、retained size、source map、自动优化、长期趋势服务列入后续候选。只有外部案例证明现有证据不足以完成用户任务时，再确定其中哪一项进入下一版本。大规模输入的耗时与峰值内存也需单独测量后再作性能承诺。
